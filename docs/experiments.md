# Experiment guide

Experiments predict observations in synthetic environments. They never execute
the action described by a fixture or generated by a model.

## Experiment types

### Single transition

A fixture supplies an environment, prior history, one proposed action, and
expected observation facts:

```bash
agentworldlab run --model mock \
  --fixture fixtures/terminal/single-transition-v1.json
```

Use `--action` only to replace the synthetic proposed action. The replacement is
still prompt data and cannot authorise host activity.

### Stateful trajectory

A trajectory contains five to ten fixed synthetic actions. Each predicted
observation is appended to the history supplied to the next turn:

```bash
agentworldlab run-trajectory --model mock \
  --fixture fixtures/terminal/stateful-trajectory-v1.json
```

Review whether created objects, file content, errors, and other state persist
consistently across turns.

### Controlled perturbation

Use the MCP and software-engineering fixtures to inject a fixed failure without
changing the host:

```bash
agentworldlab run --model mock \
  --fixture fixtures/mcp/malformed-response-v1.json

agentworldlab run --model mock \
  --fixture fixtures/swe/missing-dependency-v1.json
```

Add terminal perturbations such as permission denied, disk full, or `python`
unavailable only as fixture facts. Do not reproduce the condition on the host.

### Baseline comparison

Add another pinned, allowlisted model entry and run exactly the same fixture.
Do not compare records unless backend, precision, quantisation, fixture ID,
context/output limits, decoding settings, and cold/warm classification match, or
each difference is stated alongside the result.

## Fixture format

Every fixture is a version 1 JSON object with:

- a stable `fixture_id`;
- one of the supported domains: `terminal`, `mcp`, or `swe`;
- an `environment` object containing a synthetic description and fixed facts;
- either one `action` or five to ten `actions`;
- an `expected` object describing required facts or final trajectory facts.

Single-transition example:

```json
{
  "schema_version": 1,
  "fixture_id": "terminal-example-v1",
  "domain": "terminal",
  "environment": {
    "description": "A synthetic terminal with no connection to the host.",
    "facts": ["The simulated current directory is /workspace."]
  },
  "history": [],
  "action": "list the current directory",
  "expected": {
    "format": "json_observation",
    "required_facts": ["/workspace"],
    "prohibited_claims": ["host command executed"]
  }
}
```

Change the fixture ID when scenario meaning changes. Keep facts observable and
specific enough for deterministic checks without overfitting prose.

## Record review

Each run writes JSON and Markdown under `records/`. Review the JSON record for:

- exact host/software, model, backend, revision, precision, and fixture identity;
- cold or warm classification and all token/context limits;
- load, preprocessing, prefill, decode, total latency, and tokens per second;
- initial, peak, and post-unload system/GPU memory;
- peak temperature and thermal/timeout cancellation status;
- raw output, parsed observation, structured error, and completion status;
- deterministic automated checks and unfilled manual-review dimensions.

Complete manual review for factual consistency, trajectory consistency, realism,
formatting, failure handling, synthetic constraint adherence, and usefulness as
an agent-testing environment.

An output can be non-empty and structurally valid while still being unusable.
Do not treat an automated pass or a successful load as proof of simulation
quality or practical performance.

## Cold and warm runs

The CLI labels a run cold by default. Use `--warm` only when the relevant model,
filesystem cache, and runtime state genuinely match a warm-run definition stated
with the results. The current one-shot CLI still starts a fresh worker for each
invocation, so document what remained warm outside the worker.

## Progressive real-model limits

Start at approximately 2K input and 64 output tokens. After the initial
Transformers milestone passes, progress deliberately through 8K/512, 16K/1,024,
and finally 32K. Do not start with 128K or 256K contexts. Follow the acceptance
and rollback table in [validation.md](validation.md).
